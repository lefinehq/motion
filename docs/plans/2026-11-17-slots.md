# Slots: values that many layers follow

**Goal:** [D44](../design/decisions.md#d44-slots-are-named-values-that-layers-follow). A scene names the values a variant changes, its *slots*, and any layer value can follow one. Changing a slot changes every value that follows it:

```text
$ motion slots promo.json
accent   color   #E63946   used by 14 values
title    text    "Launch"  used by 1 value
$ motion edit promo.json '$accent=#2A9D8F'
OK 14
```

Templates already work this way. A designer puts the values meant to change on a control layer, and expressions on other layers read them. Today the import bakes those expressions ([D38](../design/decisions.md#d38-expressions-are-baked-at-import)), so the accent colour is copied into every key that read it, and a variant has to find and change all of them.

**Measured on the local corpus** (198 templates, 7,404 enabled expressions, classified by shape, with names and strings left out):

| Shape | Expressions | Templates |
|---|---|---|
| reads another layer's control, as is | 3,475 | 125 |
| reads its own layer's control, as is | 255 | 26 |
| reads a control, then simple arithmetic | 75 | 19 |
| reads a control, then other code (checkbox and menu choices, seeded wiggles) | 1,076 | 55 |
| reads another layer, no control | 720 | 47 |
| driven by time only (`wiggle`, `loopOut`) | 877 | 92 |
| other | 926 | 61 |

Half of all expressions are a control read with nothing after it. Each of those is a value following a slot.

**Done means:**
- A scene and each composition can declare slots, and any value can follow one with `$name`.
- `motion slots` lists the slots with their types, values and uses. `motion edit` sets a slot with `$name=value`.
- A `comp` layer can set its composition's slots for itself alone through `overrides`.
- The import turns control layers into slots and the plain reads into `$name`, and reports what stayed baked.
- An exported project's controls take the slots' values ([D45](../design/decisions.md#d45-export-patches-the-project-it-came-from)).

## Design

### Declaring slots

`slots` sits on the scene and on any entry of `comps`. It maps each slot's id to its value, and the value fixes its type, using the same shorthand the properties take:

```json
{"motion":1,"size":"1080p","fps":30,"dur":"5s",
 "slots":{"accent":"#E63946","title":{"text":"Launch"},"speed":1.5},
 "layers":[{"id":"badge","rect":"200x80 r12","fill":"$accent"}]}
```

- **Types.** A colour string is a `color` and a number is a `number`. `{"text":"…"}` is a `text`, and a list of two numbers is a `point`. Writing a type out, `{"color":"#E63946"}`, is always allowed. Types come from `ValueType`, so every property that has a type can follow a slot of that type ([D27](../design/decisions.md#d27-one-generic-property-model)).
- **Ids** follow the layer id rule ([D43](../design/decisions.md#d43-one-layer-address-and-edits-per-instance)).
- **Labels.** A slot may carry a `label` for people, `{"color":"#E63946","label":"Accent"}`; an import keeps the control's name there.

### Following a slot

Any value written as `"$id"` follows the slot `id`. This works for a property, a key's value in an `anim` track, and an override.

- **Escaping.** `$` followed by an id is a reference. `$$` is a literal dollar sign, so a price is written `"$$99"`. A `$` followed by anything that is not an id, as in `"$99"`, stays literal, but `check` warns about it, so a typo cannot pass silently.
- **Scope.** A reference names a slot of the composition the value is in. If that composition has no such slot, it names a slot of the scene. It never names a slot of an outer instance: what a composition can be given is exactly what it declares.
- **Checking.** `check` reports a reference to no slot and a slot whose type does not fit the value. It also reports a slot nothing follows (a warning). Each report is a diagnostic at the value, `badge.fill`.

### Instances

A `comp` layer sets its composition's slots for itself in `overrides`, next to the layer keys of [D43](../design/decisions.md#d43-one-layer-address-and-edits-per-instance):

```json
{"id":"card-2","comp":"card","overrides":{"$title":"Sale","badge/icon":{"fill":"#E63946"}}}
```

Instances are how a template repeats one design with different words. A slot set this way reaches every layer of that instance that follows it, at any depth.

### Compiling

References are resolved when the scene compiles, before values are typed. Each resolves to the slot's value, or to the instance's override of it. The graph, evaluation and drawing never see a reference, so nothing after compile changes, and a render costs nothing more. An edit to a slot drops the compiled scene, as any edit does.

### Editing and listing

- `motion edit scene.json '$accent=#2A9D8F'` sets a scene slot. `'card-2.$title=Sale'` sets an instance's slot. `'$accent=none'` is refused while a value still follows it.
- `motion slots scene.json` prints each slot of the scene and of each composition: its id, type, value, label, and how many values follow it. With `--json` it prints the same as data, which is the variant surface agents read.
- The address grammar names a slot as `$accent`, or `card/$title` inside a composition.

### Import

- **Control layers become slots.** A control layer is a layer whose effects are all controls (slider, angle, checkbox, menu, colour, point). Each of its controls becomes a slot of the composition the layer is in. The id comes from the control's name, and the label keeps the name as written. The layer itself draws nothing and is dropped, and the report says so.
- **A control on a drawn layer** becomes a slot of its composition named `<layer>-<control>`.
- **Plain reads become references.** An expression whose whole body reads one control, `thisComp.layer("Controls").effect("Accent")("Color")`, `comp("Main").layer(…)…` or `effect("Size")(1)`, becomes `$id`. `comp("Main")` names the scene when Main is the composition imported as the scene.
- **Everything else is baked as today,** and the report counts both outcomes, with the shape of each expression that stayed baked.
- **Animated controls.** A control whose value is keyframed stays baked in this plan: a slot holds one value.

### Export

A slot that came from a control remembers it. Export writes the slot's value into the control's value in the project, so the template opens with the variant's colours and words ([D45](../design/decisions.md#d45-export-patches-the-project-it-came-from)).

## Steps

Each step is one pull request, with its tests.

1. **Format.** `slots` on the scene and on comps, `$id` with `$$`, scope, types, check, and compile resolving references.
2. **Instances.** `$id` keys in `overrides`, with an error at `card-2.$title`.
3. **Edit and list.** `$id=value` edits, the address form, `motion slots` with `--json`.
4. **Import.** Control layers and plain reads, the report's counts, and the corpus measured before and after.
5. **Export.** Slots written back into the controls.
6. **Docs.** `scene-format.md`, `variants.md`, the glossary and the CHANGELOG.

## Out of scope

- **Checkbox and menu choices** (240 expressions of one shape): a `choose` value form, measured first.
- **Arithmetic on a slot** (75 expressions): a later value form, once it has a second use.
- **Animated slots,** and seeded wiggles that read a control.
- **Text runs that survive a new text** (audit workstream 7): its own plan, which text slots need before localising styled text.
