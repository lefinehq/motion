# Importing `.mogrt` templates

**Goal:** `motion import template.mogrt` gives the same scene as importing the project inside the template, plus a slot for every control the template offers ([D53](../design/decisions.md#d53-a-mogrt-imports-as-its-project-with-its-controls-as-slots)):

```text
$ motion import lower-third.mogrt --out lower-third.json
template: 9 controls, 9 slots (2 in a group)
slots   $name text "Your Name" · $accent color #E63946 · $size number 100 · …
```

## What a `.mogrt` holds

Measured on the four `.mogrt` templates kept locally (counts only):

- A zip archive of three files:
  - `definition.json`, the panel: a list of controls, each with an id, a type, a name and a value;
  - a thumbnail;
  - a nested zip that holds the project, an `.aep`.
- In the project, each control is a `CCtl` list. It carries:
  - the control's id, the same as in `definition.json`, for all 34 controls;
  - its type, value and default;
  - a `CPrp` list naming its target by composition id, layer id and a property path of match names.

| Control type | Controls | Drives |
|---|---|---|
| 2 slider | 11 | an expression control |
| 4 colour | 8 | an expression control |
| 6 text | 5 | a text document |
| 1 checkbox | 3 | an expression control |
| 3 angle | 2 | rotation |
| 5 point | 2 | position |
| 9 scale | 2 | scale, with its two values linked |
| 10 group | 1 | nothing: it holds other controls |

So 22 of 33 controls drive an expression control, which the import already reads as a slot when an expression follows it ([D44](../design/decisions.md#d44-slots-are-named-values-that-layers-follow)). The other 11 drive a layer's own property directly.

## The mapping

- **The archive.** The reader checks each entry's sizes before inflating it, caps them as it caps a project, and reads only `definition.json` and the project. A template with no project inside is refused: `the template holds no project to read (it was made in an editing app)`.
- **The composition.** The one whose `CCtl` lists the panel's controls; the import imports it as it would the project's main composition.
- **Slots by type:**
  - text becomes `text`;
  - colour becomes `color`;
  - slider, angle and checkbox become `number`; a checkbox is 0 or 1, and a slider keeps its range in the label until slots have ranges;
  - point and scale become `point`.
- **Ids and labels.** A slot's id is made from the control's name, unique in the scene. Its label is that name, with the group's name before it inside a group.
- **Followers.** The property a control drives is written `"$id"`.
  - For an expression control, the slot it already makes from the control's reads is merged into the panel's slot, so its id and label come from the panel.
  - A property with keys, or that an expression drives, stays as it is, and the report says why that control has no follower.
- **The report** adds a line, `template: N controls, M slots`, and the reason for each control that is left out.
- **Roles.** The import also proposes roles from control names, against the same vocabulary as layer names, so a `Title` control proposes `headline`.

## Steps

Each step is one pull request, with its tests.

1. **Decision.** D53 and this plan.
2. **The archive.** Read a `.mogrt` into its panel and its project bytes. Decode `CCtl` and `CPrp` into `Project::controls`. Refuse a template with no project. Tests build archives in memory.
3. **Controls become slots.** The composition, the types, ids and labels, the followers and the merge with expression-control slots, and the report line. Measured on the local templates.
4. **The command and roles.** `motion import` takes `.mogrt`, the import proposes roles from control names, and the docs (`aep-import.md`, `variants.md`, the CHANGELOG).

## Out of scope

- Templates made in an editing app, which hold their own format, not a project.
- A text control's font, size and style.
- Responsive timing and pinning.
- Media replacement controls, which none of the local templates use.
- Writing a `.mogrt` back.
