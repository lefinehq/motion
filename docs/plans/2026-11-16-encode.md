# Encode: frames into a video file

**Goal:** step 5 of the [pipeline](../design/rendering.md), under [D13](../design/decisions.md#d13-codec-licence-policy) and [D46](../design/decisions.md#d46-video-is-encoded-in-a-crate-of-its-own-behind-one-codec-trait). A scene renders straight into a video file:

```text
$ motion render launch.json --out launch.mp4
150 frames written to launch.mp4 (AV1, 1920x1080, 30 fps, 5 s)
```

Today `motion render` writes PNG frames, and a video needs another tool.

**Done means:**
- `motion render --out <file>.mp4` writes an MP4 on every platform, with no other tool installed.
- On macOS it is H.264 by default, from the system's encoder; elsewhere AV1 until the platform's own encoder lands.
- `--codec` picks the codec; a codec the platform lacks is an error that names the ones it has.
- Frames stream from the renderer to the encoder: memory does not grow with the video's length.
- The binary holds no GPL code and no patent-encumbered software encoder, and a test fails if that changes.

## Design

### One crate, three parts

`motion-encode` knows nothing about scenes. It takes frames of straight RGBA8 pixels at a fixed size and rate, and writes a file:

1. **Colour.** Each frame becomes Y′CbCr 4:2:0 in BT.709, limited range, which is what players assume for HD video. The conversion is our own small function, tested against the standard's reference values, so every codec gets the same planes. A frame's alpha is dropped for codecs without alpha; the scene's background is already in it.
2. **Codec.** One trait, `VideoEncoder`: frames in, compressed packets out, then `finish`. Each codec is one implementation, behind its own feature and platform `cfg`.
3. **Container.** One trait, `Muxer`: packets in, a file out. MP4 is our own writer on the boxes of `mp4-atom` (MIT or Apache-2.0): each packet goes to a scratch file as it comes, and at the end the file is laid out with the index ahead of the samples, so a player can start before it has all of it. Only the sample tables, a few bytes a frame, stay in memory. `muxide` was weighed first and left out: it holds every packet in memory until the file is finished.

### Codecs, by D13

| Codec | Where | From | Step |
|---|---|---|---|
| AV1 | everywhere | `rav1e` (BSD-2-Clause, pure Rust, built without its assembly) | 1 |
| H.264, HEVC | macOS | VideoToolbox, through `objc2-video-toolbox` | 3 |
| ProRes 4444 with alpha, in MOV | macOS | VideoToolbox | 4 |
| H.264 | anywhere, on request | Cisco's OpenH264 binary, loaded at run time through `openh264` with only its `libloading` feature | 5 |
| H.264, HEVC | Windows; Linux with a GPU | Media Foundation; VA-API or NVENC | later |
| VP9, AV1 in WebM | everywhere | needs a Matroska writer and VP9 bindings under a permissive licence; neither exists yet | later |

AV1 comes first because it runs everywhere, including CI, with nothing installed, so the whole path is tested before any platform encoder.

OpenH264 is never compiled in. Like fonts ([D39](../design/decisions.md#d39-fonts-are-resolved-before-a-render)), the binary comes from a separate command that records its version and hash; a render loads it from the cache, checks the hash, and never touches the network ([D14](../design/decisions.md#d14-no-network-while-rendering)).

### Streaming

The renderer draws frames on every core, out of order. The encoder needs them in order, one at a time. `Session::render_in_order` draws in parallel and hands frames over in order; a thread that draws too far ahead waits, so at most two frames per thread are held. The engine does not link the encoder: the CLI joins the two. The `render` and `encode` stages are timed apart, so a slow encoder shows up in `--timings`.

### Choosing the output

`--out` decides: a folder gets PNG frames as today; a file name's extension picks the container (`.mp4`, later `.mov` and `.webm`). `--codec` picks the codec, by default the first the platform has of H.264 and AV1. Quality is a target, not a bitrate: `--quality` already exists for drawing, so encoding gets `--crf`-like levels named by use (`draft`, `web`, `master`), each a row in one table per codec.

### Tests

- **Colour:** the BT.709 reference colours convert to their published Y′CbCr values, and a grey ramp stays grey.
- **Container:** the MP4 has the right sample count, timescale, duration and dimensions, read back with `mp4-atom`.
- **AV1:** with one thread and a fixed speed, `rav1e` is deterministic, so the same frames give the same file, byte for byte. A pinned hash would break on every `rav1e` release without telling us anything more.
- **Platform codecs:** run on the platforms that have them (macOS runs in CI), checking the file reads back and decodes to frames close to the drawn ones.
- **Boundaries:** no crate that reads, compiles or draws a scene links `motion-encode`; `openh264`'s `source` feature is never enabled anywhere in the tree.

## Steps

Each step is one pull request, with its tests.

1. **`motion-encode` with AV1 in MP4.** The colour conversion, the two traits, the MP4 writer and `rav1e`; frames drawn in parallel and handed over in order; `motion render --out x.mp4` writes AV1.
2. **The CLI.** `--codec`, quality levels, the `encode` stage in the timings.
3. **VideoToolbox on macOS.** H.264 and HEVC, and H.264 as the default there.
4. **ProRes 4444 with alpha in MOV**, for scenes with a clear background.
5. **OpenH264 on request.** `motion codecs fetch`, the lock, the cache and the run-time load.
6. **Docs.** `rendering.md` as built, the CLI help, the CHANGELOG.

## Out of scope

- **Audio:** placing, trimming and mixing sound is its own plan.
- **WebM, Windows and Linux GPU encoders:** each waits for the pieces in the table above.
- **Chunked renders across processes:** the frames are independent, so this needs only joining, later.
